# 07. 中断、并发与运行控制规范

## 1. 中断服务函数

中断服务函数只执行必要的实时动作：

- 判断中断源。
- 读取或写入外设数据寄存器。
- 清除中断标志。
- 将数据写入缓冲区或 FIFO。
- 更新状态机。
- 置位事件标志，通知主循环或任务处理。

中断中禁止执行以下操作：

- 延时函数或无超时轮询。
- `printf`、`sprintf`、复杂格式化和动态内存操作。
- 长时间 CAN/UART 阻塞发送。
- 复杂 PID、路径规划、舵机运动编排和业务决策。
- 可能再次触发同一中断的不可控操作。

现有 USART2、UART5、CAN 和定时器中断的处理逻辑应作为后续优化参考；新增中断代码必须保持短小、可预测和可恢复。

## 2. 中断与主循环通信

推荐使用“中断采集、主循环处理”的模式：

```c
static volatile bool uart_frame_ready;

void USARTx_IRQHandler(void)
{
    uint8_t byte;

    if (USART_GetITStatus(USARTx, USART_IT_RXNE) != RESET)
    {
        byte = (uint8_t)USART_ReceiveData(USARTx);
        uart_protocol_push_byte(byte);
        uart_frame_ready = true;
        USART_ClearITPendingBit(USARTx, USART_IT_RXNE);
    }
}
```

共享数据必须定义所有权：中断负责写入、主循环负责读取，或者通过 FIFO/双缓冲转移所有权。读取多字节数据时应避免读取到一半被中断更新的状态。

## 3. 主循环

`main` 应负责：

- 系统时钟和基础服务初始化。
- 各模块初始化及初始化顺序控制。
- 顶层状态机或周期任务调度。
- 处理由中断置位的事件。
- 统一故障状态和安全停机。

主循环不应堆叠全部业务细节。新增业务应拆为命名清晰的状态或处理函数，并明确进入条件、退出条件和异常路径。

## 4. 延时和轮询

- 函数名必须体现时间单位，例如 `delay_ms`、`delay_us`、`wait_timeout_ms`。
- 延时函数注释必须说明是否关闭中断、是否允许在中断中调用以及最大延时。
- 所有等待外设标志、接收帧、运动完成和控制完成的轮询必须有超时或故障退出机制。
- 无法避免的阻塞等待必须记录原因，并提供 LED、OLED、串口或其他方式的故障指示。
- 不在中断中调用阻塞延时。

## 5. PID 和运动控制

- PID 参数、采样周期、角度单位、速度单位、输出上下限必须写在结构体或配置常量中。
- 控制周期必须与实际定时器周期一致，禁止依赖隐含的固定 `50 ms` 等数值。
- 角度应明确采用度、弧度或有符号范围，不能仅使用 `angle`、`target` 等无单位名称。
- 积分项必须有上限，输出必须有安全限幅，切换目标或重新启动运动时必须明确积分清零策略。
- 电机、舵机和平台动作必须具备初始位置、运动完成、超时和异常停机处理。
- 运动函数不应直接暴露大量无单位的裸参数；必要时使用配置结构体或具名参数封装。
